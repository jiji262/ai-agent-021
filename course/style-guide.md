# 课程写作风格指南

> 这份文档是所有写章节的子代理的**唯一文风权威**。
> 写一节之前先把这份读完，每一节交付前对照本指南自检一遍。

---

## 0. 一句话总纲

**「公众号叙事的腔调 × 体系课的骨架 × 生产代码的可信度」**——这门课要让读者**看得下去、学得到、用得上**。

- 看得下去：开头 200 字必须是一个真实场景或痛点，钩子先打到读者
- 学得到：每节有清晰小结 + 思考题，读完知道自己学会了什么
- 用得上：每段代码都对应到 `https://github.com/jiji262/ssp-web` 的真实文件，能跑能改

---

## 1. 每节固定结构（七段式）

每一节按以下顺序展开。**段名可以微调（如"故事开场"换成"从一个 bug 说起"），但顺序和功能不能变**。

| 顺序 | 段名 | 字数 | 必含元素 |
|---|---|---|---|
| 1 | **Hero 封面 + 元信息** | 极简 | 一张封面图 + 阅读/实战时长 + 前置知识 + 本节代码 tag |
| 2 | **引入故事（开场钩子）** | 200-400 | 真实痛点/场景/对话/bug/问题。**禁止从概念定义开始** |
| 3 | **知识铺垫** | 500-800 | 把本节要用到的概念/术语/前置原理讲清楚。**像和朋友解释新概念** |
| 4 | **核心讲解** | 2500-4000 | 主体。代码 + 配图 + 决策表 + 反例 |
| 5 | **举一反三** | 300-500 | "这个原则换到法律咨询/医疗问诊/金融规划怎么用" |
| 6 | **小结 + 收束图** | 200-400 | 一段总结 + 一张小结卡片图 |
| 7 | **思考题** | 2-3 题 | 1 道开放讨论 + 1 道动手落地 + 0-1 道选做进阶 |
| 8 | **面试题** | ≥3 题 | **主线节（02–29 节）必含**。固定 `## 面试题` 段，每题带难度 + 主题 + 折叠式参考解答（格式见 §8.3） |
| 9 | **延伸阅读** | 极简 | 3-5 个外链：官方文档 / 论文 / 优秀实践 |
| 10 | **导航** | 1 行 | 上一节 · 目录 · 下一节 |

> 「面试题」段只对主线节（`02-*.md`–`29-*.md`）强制；开篇词、序章、结束语、加餐、FAQ 不要求内嵌面试题。其余八段对全部正文 Chapter 通用。

**字数总目标**：每节 4000-6000 字。低于 3500 = 内容薄；高于 6500 = 没拆好。
**主线节硬门禁**：正文字数必须落在**闭区间 [4000, 6000]**（校验器 `checkWordGate` 以此为准，超出即告警，不静默通过）。面试题与思考题的题面/解答**计入**正文字数。

## 3. 文风：公众号叙事 + 体系课严谨

### 3.1 该这样写

- **从场景钩子开始**："你有没有试过……"，"那天产品经理在群里发了张截图……"
- **用第二人称（你）**：拉近距离
- **金句收束段落**："核心区别就一句话：Agent 能自己决定下一步做什么"
- **形象比喻**："LLM 是嘴，规则引擎是脑"，"prompt 是手册，tool 是手脚"
- **真问题驱动**："为什么 ChatGPT 算不对你的退休年龄"
- **数字说话**："24 条规则"、"成本降低 60%"、"延迟从 800ms 到 200ms"
- **结构化清单**：3 件事 / 4 个原则 / 5 个步骤
- **Markdown 视觉节奏**：表格 / 代码块 / 引用块 / 加粗 交替使用，避免大段纯文字

### 3.2 别这样写

- ❌ "首先，我们来介绍一下 Agent 的概念"——空话开场
- ❌ "AI Agent 是一种基于大语言模型的智能体系统"——百度百科腔
- ❌ "众所周知"、"显而易见"、"毋庸置疑"——没有信息量的填充
- ❌ "亲爱的同学们"——油腻
- ❌ 整段连续超过 5 行不分段
- ❌ 章节里突然冒出"我们"="作者"+"读者"的混淆，全文统一用"你"指读者，"我们"=作者团队
- ❌ 不交代版本号的 API（"用 streamText 这个函数"——必须说"AI SDK v6 的 `streamText`"）
- ❌ 提及本课程的历史版本或做版本对比（详见 §3.3 硬规则）

### 3.3 版本措辞硬规则（全课程零容忍）

**本课程对读者表现为唯一的一门课，不存在"历史版本"。** 任何章节（含开篇词、序章、正文、加餐、FAQ、README、导航）一律**不得**提及本课程曾有过其他版本，也不得做版本对比。

**禁用词表（命中即判违规，校验器 `detectForbiddenPhrases` 据此扫描）**：

- 「v1」「v2」（指代本课程版本时）
- 「历史归档」「旧版本」「老版本」「上一版」「升级说明」「版本对比」「重写前」

✅ 正确：直接讲当前内容——「本节我们用 AI SDK v6 的 `streamText`……」
❌ 错误：「相比 v1 教程，这一版我们改用了……」「旧版本里这一章讲的是……」「（历史归档见根目录）」

> 注意：这条规则约束的是**指代本课程自身版本**的措辞。客观描述**第三方技术栈**的版本号是必须的、不受限（如「AI SDK v6」「Next.js 16」「next-auth v5」——见 §3.2 必须交代 API 版本）。区分关键：版本号是修饰**别人家的库**就写，是修饰**本课程**就删。

## 4. 代码引用规范

### 4.1 引用真实文件

**所有代码片段必须能在 `https://github.com/jiji262/ssp-web` 找到对应位置**。引用格式：

```typescript
// src/lib/ai/agent.ts:42-65
export async function POST(req: Request) {
  const { messages, userProfile } = await req.json();
  // ...
}
```

文件路径开头标注，必要时加行号范围。如果是修改示意而非真实代码，**明确标注 `（示意，非项目实际代码）`**。

### 4.2 代码片段长度

- 单段最长 30 行。超过 30 行就拆成两段，中间用文字解释。
- 关键 5-10 行用 `> **看这里 →**：[解释]` 紧跟其后突出。

### 4.3 何时贴完整代码、何时贴 diff

- 引入新文件 → 贴完整结构（仅关键导出 + 注释占位）
- 修改既有文件 → 用 `// ... 不变` 标省略，只贴改动
- 演示重构 → 贴 before / after 两段对照

### 4.4 不要贴的代码

- 配置文件全文（如 `tsconfig.json` 全部）→ 只贴关键字段
- 自动生成的代码（如 drizzle migration 全文）→ 说明，给链接
- 长 schema 全文（如 24 条规则全部）→ 贴一两条作为示例

## 5. 图片引用规范

### 5.1 路径与命名

```
images/
├── NN-hero.png         ← 每节封面，必有
├── NN-NAME.png         ← 每节内插图，NAME 为 kebab-case
└── shared/
    └── ssp-overview.png ← 跨节复用图
```

NN = 节号（00、01、02、...、29、30）。开篇/结束/加餐/FAQ 用：

- 开篇词：`prologue-hero.png`、`prologue-NAME.png`
- 序章：`00-...`
- 结束语：`epilogue-hero.png`
- 加餐：`extra-1-hero.png`、`extra-1-NAME.png`
- FAQ：`faq-hero.png`、`faq-NAME.png`

### 5.2 图片密度

每节最少 **5 张图**：

- 1 张 hero 封面（开篇必须）
- 1 张概念示意（铺垫段）
- 1-2 张架构/流程/决策（核心讲解段）
- 1 张小结卡片（结尾必须）

理想 7-10 张。**不要只放截图**，要有原创示意图。

### 5.3 图片样式

- **手绘风格**：所有概念图、人物相关图、隐喻类图（如"金鱼脑"）
- **信息图风格**：架构图、对比矩阵、决策树、时序图（用 baoyu-infographic）
- **截图**：UI 演示，必须加注释/箭头/高亮

### 5.4 引用语法

```markdown
!\[描述性 alt 文本，便于无障碍访问\](images/NN-name.png)
```

**禁止**仅用 `<img>` 标签或加 width 内联样式。

### 5.5 图片路径硬规范（删 V1 后零坏图）

本课程的规范图片目录是 `course/images/`。根目录 `ai-agent-021/images/`（V1 时期的图片目录）**已被删除**，任何指向它的路径都会坏图。引用路径按文件所在层级区分：

- **顶层章节**（`course/` 直接子文件，如 `02-what-is-agent.md`、`README.md`）：**必须**用相对 `course/` 的路径 `images/...`。
  - ✅ `!\[...\](images/02-hero.png)`
  - ❌ `!\[...\](../images/02-hero.png)`——`../images/` 从顶层逃出 `course/` 指向已删除的根目录，**严禁使用**。
- **`extras/` 子目录章节**（如 `extras/01-admin-cms.md`）：图片引用用 `../images/...`，它从 `course/extras/` 正确解析回 `course/images/`，**这是正确写法**，保持不动。
  - ✅ `!\[...\](../images/extra-1-hero.png)` → 解析到 `course/images/extra-1-hero.png`
  - ❌ `!\[...\](images/extra-1-hero.png)`——会错误指向不存在的 `course/extras/images/`。

> 一句话记忆：**所有图片引用最终都必须解析到 `course/images/` 下的真实文件**。顶层用 `images/`，`extras/` 用 `../images/`，绝不指向根目录 `ai-agent-021/images/`。校验器 `classifyImagePath` 按 scope（top / nested）做合规判定，顶层出现 `../images/...` 即记 `bad-image-path`。

## 8. 思考题写作规范

每节末 2-3 题。

### 8.1 三种题型

- **开放题**：没有标准答案，鼓励读者结合自己项目思考
  - 例：「你的项目是否真的需要 RAG？读完本节后说说为什么。」
- **动手题**：在本地能跑通的小练习，必须给**验收标准**
  - 例：「修改 `system-prompt.ts`，让 Agent 在第二轮就能识别用户提问意图。验收：跑 `pnpm test:eval` 通过率 ≥ 90%。」
- **进阶题**：选做，挑战性大
  - 例：「实现一个自定义的 LLM-as-Judge，评分 prompt 复用本节的 rubric，跑过 50 条历史用例并给出 win-rate。」

### 8.2 别这样写思考题

- ❌ "回顾本节内容"——这是复习不是思考
- ❌ "举例说明 Agent 的优势"——开放题应该挑战立场，不是要列优点
- ❌ "请课后阅读延伸资料"——废话

### 8.3 面试题段（主线节必含，格式严格可解析）

每个主线节（`02-*.md`–`29-*.md`）在「思考题」之后、「延伸阅读」之前，固定一个 `## 面试题` 段，**至少 3 道**，面向 AI Agent 岗位面试候选人。这些题会被解析器抽取并汇总进 `interview-questions.md`，因此**格式必须严格统一**。

**单题格式（逐字符约定）**：

```markdown
**Q1.【难度】【主题：X】** 题面正文写在同一行……
<details><summary>参考解答</summary>

参考解答正文。可换行、可分点、可带代码块。

</details>
```

逐项约定（供 `parseInterviewQuestions` 解析、`validateQuestionMeta` 校验）：

| 字段 | 约定 | 说明 |
|---|---|---|
| 题号 | `**Q1.** **Q2.** …` | 加粗，`Q` + 序号 + 英文句点，节内从 1 递增 |
| 难度 | `【难度】` | **必须 ∈ {基础, 进阶, 深挖}**，方括号内不加其他字 |
| 主题 | `【主题：X】` | `X` **必须属于 `knowledge-map.md` 的主题集**（如 `Tool Calling 协议`、`MCP`、`RAG` 等）；中文全角冒号 `：` |
| 题面 | 紧跟在 `**` 标记之后，同一行起 | 非空 |
| 参考解答 | `<details><summary>参考解答</summary>…</details>` | `summary` 固定写「参考解答」；解答正文非空，且与本节正文技术陈述一致 |

**完整示例**：

```markdown
## 面试题

<details><summary>参考解答</summary>

</details>

<details><summary>参考解答</summary>

repairToolCall 把校验错误回灌给 LLM 让其重出参……边界在于……
```

**约束清单**：

- 每个主线节 **≥3 题**，每题**必须**带 `<details>` 折叠参考解答，解答非空。
- 难度三选一：**基础 / 进阶 / 深挖**（不要写「中级」「困难」等同义词）。
- 主题取自 `knowledge-map.md`，**不要自创主题词**；若确需新主题，先扩充 `knowledge-map.md` 再用。
- 同一节内的面试题应覆盖本节核心知识点，难度宜有梯度（基础打底 + 进阶/深挖拔高）。
- 面试题与「思考题」是**两个独立段**：思考题考查动手与发散思考，面试题考查可被追问的知识点；不要互相替代。

### 8.4 别这样写面试题

- ❌ `**Q1.（进阶）** ……`——括号不对，难度必须用 `【】` 且为三值之一
- ❌ `**Q1.【中等】【主题：工具】** ……`——难度越界 + 主题不在 knowledge-map
- ❌ 题面后不写 `<details>` 解答，或解答只写"略"——解答必须实质、非空、与正文一致
- ❌ "下列哪个选项正确？A… B… C…"——本课面试题是简答/论述题，不做单纯选择题

## 10. 跨节连贯性约束

### 10.1 概念引入顺序

- 第一次出现的概念必须在**核心讲解**段定义
- 后续章节使用时直接用术语，不再展开（除非角度不同）

### 10.2 故事线连贯

- 主线案例：用户"小赵 1975 年女性"贯穿大部分章节，避免每章发明新人物
- 例外：极少数章节需要新场景，可以引入，但不要在每节都引入新角色

### 10.3 SSP 架构演进

- 入门篇：架构鸟瞰，不展开实现
- 基建篇：项目跑起来，但还没有核心逻辑
- 核心篇：填充推理层和执行层
- 工程篇：补全交互层和持久层
- 进阶/演进篇：在已有架构上"加挂件"

不要在 02 节就讲 RAG，也不要在 26 节才介绍数据库。
